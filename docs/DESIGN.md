# Дизайн и план

Сводка решений из обсуждения. Отмечено, что уже сделано, а что в планах.

## 1. Счётчики — сделано

- Два уровня: **андезитовый** (бытовой) и **латунный** (промышленный).
- Энергия: вход сверху → буфер (2 × лимит) → выходы сзади и снизу. Учёт по факту принятого.
- Лимит на тик берётся из конфига по уровню.

**Следующее по счётчикам:**
- ~~настраиваемый лимит в коридоре уровня~~ — сделано меню лимита (ПКМ пустой рукой);
- латунный: двухтарифный учёт (день/ночь Minecraft), приём и отдача отдельно (продажа излишков);
- латунный: сигнал компаратора, лампа состояния (зелёная/жёлтая/красная).

## 2. Пломба — главное звено (сделано)

Сделано: `SealRegistry` (SavedData, состояния INSTALLED/BROKEN/REVOKED, журнал поставщика до 100 событий), предмет пломбы, свойство `sealed`, фильтр в трансформаторе. Упрощение относительно плана: отдельной стадии ISSUED нет — поставщиком становится тот, кто ставит пломбу. Журнал пока только хранится, показывать его будет терминал.


Счётчик может скрафтить кто угодно. **Без пломбы** он работает как обычный измеритель (для своей энергии). **Пломба** нужна, чтобы получать энергию из сети поставщика.

- Пломбу выдаёт и ставит только поставщик. Она привязана к лицевому счёту абонента.
- Одноразовая: сломал/перевесил счётчик → пломба сорвана, запись в журнале поставщика.
- Подлинность проверяет **сервер**, а не предмет: реестр `SealRegistry` в `SavedData`.
  - `Seal { id, supplier, account, dimension+pos, state: ISSUED | INSTALLED | BROKEN | REVOKED }`
  - в предмете только `sealId` (data component);
  - одна пломба — один счётчик в конкретном месте;
  - поставщик может отозвать пломбу (удалённое отключение).
- В блокстейте свойство `sealed` → модель с пломбой или без.

## 3. Сеть поставщика — сделано (без пломб)

Сделано: трансформатор (`line_transformer`), коннектор (`line_connector`), провод (`line_wire`); счётчик получает энергию только по линии. Подстанцию из плана пока заменяет трансформатор, владелец — тот, кто его поставил. Фильтр «только счётчики с действующей пломбой» добавится вместе с пломбами.


Изучено, как устроены провода Create: New Age (ветка 1.21.1):
- провод — не блок, а связь между коннекторами (`Map<BlockPos, WireType>` в BlockEntity), рисуется рендерером коннектора;
- предмет провода: клик по первому коннектору сохраняет позицию в data component, клик по второму соединяет;
- сеть — граф коннекторов; потребители — опорные блоки, принимающие энергию; распределение поровну по кратчайшему пути;
- `WireType` — enum, поэтому свой тип провода туда не добавить. Лицензия BSD-3: логику можно адаптировать с сохранением копирайта.

Наше решение — **своя изолированная иерархия** (их провода не цепляются к нашим узлам и наоборот):

| Класс | Роль |
|---|---|
| `SubstationBlock` (подстанция) | точка входа энергии поставщика (тянет из его аккумулятора), владелец сети, общий лимит, рубильник, интерфейс поставщика |
| `PoleBlock` | опора/изолятор для длинных линий |
| `ServiceCableItem` | сервисный кабель; соединять может только владелец узлов |
| счётчик | конечный узел, кабель подключается к верхней клемме |
| `ServiceNetwork` | потребители — **только счётчики с действующей пломбой этого поставщика и без отключения за долг** |

Подстанция также считает, сколько отдано в сеть: разница с суммой счётчиков больше потерь → хищение.

## 4. Оплата — постоплата с лицевым счётом (сделано)

Сделано: `BillingData`, терминал (`billing_terminal`), квитанции по периоду, стадии долга, расцепитель андезитового счётчика. Упрощения: тариф общий на поставщика, а образец валюты — свой у каждого терминала; квитанция — сообщение в чат, а не предмет; двухтарифность и Numismatics пока не сделаны.


- У абонента **лицевой счёт с балансом**. Можно пополнять заранее, начисления списываются в конце периода; минус — долг.
- Пополнение: касса подстанции/терминала, валюта — **любой предмет** на выбор поставщика (сравнение `ItemStack.isSameItemSameComponents`), а также редстоун-импульс от **Депозитора Create: Numismatics** (без зависимости от их кода).
- Долг висит на счёте игрока, а не на блоке: новый счётчик не обнуляет долг.

### Стадии при неоплате (сроки — в конфиг)

| Стадия | Что происходит |
|---|---|
| Квитанция | конец периода, начисление, сообщение абоненту |
| Предупреждение | лампа жёлтая, щелчки и текст в action bar |
| Ограничение | лимит падает до 10–20 % |
| Отключение | реле щёлкает, индикация гаснет, лампа красная, бирка «Не включать» |

- **Андезитовый**: при отключении срабатывает расцепитель; после оплаты включает только электрик/владелец ключом.
- **Латунный**: ограничивает мощность и включается сам после оплаты; управляется удалённо.

Стадии двигает `ServerTickEvent` раз в игровой день по данным `SavedData`, независимо от загрузки чанков. Счётчик в `push()` смотрит только на стадию своего счёта.

## 6. Панель поставщика и цифровая валюта (сделано)

- Два трансформатора: андезитовый (только FE → линия) и умный латунный с панелью поставщика.
- Панель: абоненты (удалённое отключение, потолок мощности, счёт одному/всем), валюта, касса.
- Баланс — в кредитах. Валюта — до 6 предметов с ценой; слоты «призрачные», как фильтры Create.
- Оплаченные предметы уходят в общую кассу поставщика (`BillingData.Supplier.vault`), терминал ничего не хранит. Старые кассы терминалов переносятся туда при загрузке.
- Настройки общие для всех терминалов и панелей поставщика.
- Действия клиента — через clickMenuButton; списки абонентов и кассы — один S2C-пакет `PanelSyncPayload` раз в секунду, пока панель открыта.

## 7. Автоматика (сделано)

- **Электрокатализатор** — один блок вместо воды/костра/лавы/призрачного огня перед вентилятором. Режим — переключатель Create (`ScrollOptionBehaviour`) или сила сигнала. Питание FE, расход по режиму.
  - Без своих `FanProcessingType`: блок в тегах `create:fan_processing_catalysts/{smoking,blasting,haunting}` и `create:fan_transparent`, а режим задаётся свойствами `blaze` и `flame_type` горелки ифрита (Create проверяет именно их). Промывка — `getFluidState` отдаёт воду; блок полный, жидкость не рисуется и не течёт.
  - Ближние вентиляторы (до 3 блоков) получают `blockInFrontChanged()` сразу, дальние перепроверяют поток сами раз в ~1.5 с.
- **Настраиваемый передатчик** — свой блок с `LinkBehaviour.transmitter` Create, поэтому полностью совместим с сетью связей. Сила — `ScrollValueBehaviour` 0–15. Селектор: импульс защёлкивает, остальные селекторы той же частоты (`getNetworkKey`) гаснут; после загрузки чанка побеждает нажатый позже.
- Описания предметов — `ItemDescription.Modifier` Create (ключи `.tooltip.summary/conditionN/behaviourN/controlN/actionN`).
- Идея на потом: ручной пульт (как связанный контроллер Create) с кнопками «отправить силу N».
